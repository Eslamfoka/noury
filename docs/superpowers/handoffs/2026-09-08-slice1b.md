## Two things worth knowing about how they were built

**Reminders and the adhan can no longer delete each other.** This was a real
bug found while wiring the feature, not a hypothetical. `RollingWindowScheduler
.rearm()` opened with `gateway.cancelAll()`, which clears *every* pending
notification. Any settings change after writing a reminder would have silently
taken it away, and the row would still be sitting in the calendar looking
armed. The window now clears with `cancelAllBelow(kOutOfWindowIdBase)` —
everything it owns, nothing it does not. On a Slice-1-only install this is
identical to the `cancelAll` it replaces, since there is nothing above the base
to spare.

**Two Quran wird tests on Home were already failing** before any of tonight's
work — they fail at `4a57bcb` too, so the "474 passing" in the old STATUS was
stale. `scrollUntilVisible` stops when the target is *built*, and a lazy
ListView builds 250px past the viewport, so the helper left the wird card
103px below the fold where `tap()` missed it and did nothing. It looked
date-dependent because the content above changes height with the day's prayer
times. Fixed with `ensureVisible` in the shared helper.

## Decisions I took alone

The standing constraints say to take the safest reversible option, document it,
and continue. Four came up.

1. **No new bottom tabs.** Six is already one past the recommendation and the
   tab structure is an open Slice 2 question, so: walking and workouts inside
   البدن, challenges inside التقارير, the calendar behind a Home header button.
   Nothing about the shell changed, so every answer you might give is still
   available.
2. **Workout "videos" are vector frames, not footage.** You asked for
   "exercise videos as frames". Each exercise is two to four poses of thirteen
   joints, interpolated and drawn — a few hundred bytes each, offline, no
   codec, no `video_player`, sharp at any size. Real footage can replace it
   behind the same widget later.
3. **The mushaf is typeset, not images.** An image cannot scale with your text
   size, cannot be selected, and would add megabytes. More importantly,
   typesetting means the words on screen are provably the words in the asset:
   the `quran` block holds the same text split at ayah boundaries, and loading
   *fails* if the split does not reproduce the original exactly. So
   `docs/athkar-verification.md` is still valid and its 45 unchecked athkar are
   untouched.
4. **No foreground service for walking.** The session counts while its screen
   is open and reconciles on resume, because Android keeps counting in the OS.
   Surviving a locked screen for an hour, or the app being killed, needs a
   foreground service — bigger work, and it pairs naturally with the adhan
   service already sketched in the previous handoff. Deferred, not forgotten.

## One thing I left alone on purpose

The athkar repeat pill reads **«٣ / ٠»** when you are at zero of three, because
RTL lays the slash form out right to left. It is a genuine misreading, but it
is the same form `DhikrCard` and the finance screen have always used, so fixing
it on the new card alone would make the app inconsistent, and changing it
everywhere is your call rather than mine at 3am. The fix is one line per site:
use the «٠ من ٣» form the athkar stepper already uses right above it.
