## First: the test suite was red before I touched anything

`STATUS` said 837 passing. On a clean tree at `8ba2108` it was **836 passing,
one failing** — and nothing had been committed between the green run and the
red one. Only the date had changed.

`day_rollover_test`'s "it changes once a day, not once a tick" emitted its
seeding clock tick *before* subscribing. The override is a broadcast stream,
which drops anything emitted while nothing is listening, and
`currentDayProvider` falls back to `DateTime.now()` until its first event
arrives. So the provider was built holding the machine's real date. On
7 September that equalled the ticks that followed, nothing changed, and the
count stayed at 0 — **the assertion held for the wrong reason.** On the 8th
the first tick moved the value off the real date, which is one legitimate
change, and it failed.

The provider is right; in production the clock yields `DateTime.now()`
synchronously, so the fallback covers a single frame. The test was wrong, and
it was wrong on the 7th too — it just could not fail that day, because it was
asserting nothing. It subscribes before seeding now, and asserts the seeded
value landed, so a dropped tick fails loudly instead of quietly becoming a
no-op. Verified date-independent by running the whole file shifted to 2030.

## The two things you reported from the phone

### The ± buttons swallowed three taps out of four

> «لما باجي ادوس ع الزائد او الناقص عشان ازود او أقلل وقت الإقامة في كليكات
> كتير غلط يعني ممكن ادوس ٣ او ٤ مرات عشان يزود او يقلل»

The cause was already written down in the code. `DeferredSchedulerPort`'s own
doc comment measures a window re-arm at **~11.7 seconds** — 262 sequential
platform-channel calls — and every stepper tap awaited one before the screen
refreshed:

```dart
await controller.updateIqamaOffset(entry.key, entry.value + 5);
ref.invalidate(settingsProvider);   // eleven seconds later
```

So the row held its old number for eleven seconds, and every tap in that window
recomputed `shown + 5` from that same stale number and wrote it again. Four
presses, one move.

**Measured, not reasoned.** With the old code restored behind a scheduler that
does not return until released, the four-tap test does not fail an assertion —
it times out at 30 seconds, because the tap itself never comes back.

Two faults, both fixed. The step is now a **delta resolved against the row**,
not an absolute computed from the screen, so overlapping taps compound — which
is what a button pressed twice means. And the write and the re-arm are
**separated**: `_requestRearm()` returns at once and coalesces, so a burst of
taps costs one re-arm after the burst instead of one each, which would have
been 47 seconds of work for a setting changed once.

Every other settings write that rebuilt the window — location, method, madhab,
the channel toggles, the fasting flag — is converted too. None of them should
have been holding the UI for eleven seconds either.

### قيام الليل (§5.1)

The one item in the religious pillar with no code at all — `grep -rn "قيام"
lib/ test/` returned nothing.

Computed from the night rather than a clock hour: the last third runs from
`isha + ⅔ × (fajr − isha)` to fajr, so it follows the sun through the year.
Nouri waits twenty minutes past its opening — the opening is often barely past
midnight, a strange hour to be woken — and never comes within 45 minutes of
fajr, where it would arrive as a second fajr alarm saying something different.

Two cases return nothing at all. **A night shift**, because you are at work
from 22:00 to 07:00 and every minute of the last third is duty time: a reminder
then is noise, and Nouri would be asking for something it knows cannot be done.
And a night too short to divide.

**Off by default**, unlike every other religious reminder. The others arrive
during waking hours; this one wakes you at two in the morning for a voluntary
prayer, and that is not something an app should decide for you. الإعدادات →
الإشعارات → قيام الليل.

### مكالمات (§5.5)

"One hour, placed by shift." It existed in `example_day.dart` — the day worked
out by hand — and nowhere else, so the real planner had never placed it. **The
example was promising an hour the app did not schedule.**

After work on a morning shift, in the evening on the others: on a night shift
that is the only stretch which is both awake and free before duty starts at
22:00. "During it if there's a chance" is not something Nouri can know, so it
takes the half it can and never claims the call happened during duty.

### وقت الموبايل (§5.5)

"Nouri reserves a fixed slot and notifies if exceeded." Neither half existed.

**A decision taken alone, and it is decision 7 in
`docs/planner-decisions.md`.** "Notifies if exceeded" could mean reading real
device usage. That needs `PACKAGE_USAGE_STATS` — a special-access permission
granted through a system settings page, invisible to the emulator, and the
heaviest privacy permission an Android app can hold. It would also make Nouri
**infer** where every other pillar **asks**: a fasting day is your word, a
prayer is logged rather than detected. So you report the sitting and Nouri
keeps the total.

Sittings rather than a running timer, for now — the same shape as وقت المعرفة,
which keeps the two cards legible together. A timer slots in behind the same
card later without changing anything stored.

"Hard-ish" is honoured by **saying**, never by blocking. Nouri cannot stop
anyone using their phone and would be wrong to pretend it can, so passing the
cap is a stated number — gold, not red, because an hour on the phone is not a
failure. The planner reserves an evening block the length of the cap, which is
what stops phone time eating the hours the rest of the day was planned into.

### The gentle budget note (§5.4)

`BudgetStatus` already knew how to tell a worrying number from an ordinary one.
`pacedAllowance` exists precisely so that 60% of the food budget reads as fine
on day 18 and worth noticing on day 4, and its own comment says "this is what
makes an alert useful rather than alarming". **All of it was on the finance
screen and none of it ever reached you.**

Three rules keep it a note rather than a nag, each with a test: one line
however many categories are stretched; nothing unbudgeted is judged (a limit of
zero means "not budgeted", not "overspent by everything spent"); and **صدقة is
never flagged for running ahead**, because giving early is not overspending and
a nudge reading "slow down on the charity" would be Nouri saying something it
has no business saying.

## The one piece of infrastructure this needed

The slot space was full — 31 slots against `kSlotsPerDay = 32` — and STATUS
said raising it "renumbers every alarm already on a device, so it needs a
deliberate re-arm rather than a quiet bump". This was that deliberation.

**Widening to 64 is safe for exactly one reason**, and the constant now carries
it: `cancelAllBelow` does not recompute the IDs it cancels. It reads
`pendingNotificationRequests()` from the plugin and cancels every pending alarm
below the ceiling, whatever its number — so the first re-arm after the upgrade,
which happens on the next launch, finds the old-stride alarms and removes them.
Nothing is orphaned, and reminders above the base are still spared.

A test states that property directly, using an ID no current slot can produce,
so the safety argument fails loudly if the clearing strategy ever changes back.

## Two real bugs found while building, both by tests

**The background re-arm could outlive the database.** Making the re-arm
non-blocking means nobody awaits it, so a throw becomes an unhandled
asynchronous error rather than reaching a caller. A test that closed its
database mid-re-arm found it. It is caught now, with the reasoning written
down: the window is rebuilt from scratch on the next launch, so losing one
costs nothing, and genuine scheduling failures still surface through
`NotificationStatus`.

**The phone card's header row overflowed by 32 pixels** once the day passed 90
minutes, which draws the yellow-and-black stripe on a real screen. Found by a
widget test, not reasoned about. The corner carries a short counter now —
«٩٠ من ٦٠», never a slash — and the sentence moved to the line below.
